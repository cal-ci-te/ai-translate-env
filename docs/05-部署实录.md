# 05 · Qwen3-8B 本地部署实录

> 从零到跑通的完整过程与决策依据。换机器、换模型时按这篇的思路走即可。

## 目标与约束

| 目标 | 约束 |
|---|---|
| 本地网页翻译，隐私自持、零 API 费用 | 显卡只有 **8 GB 显存**（RTX 4060 Laptop） |
| 技术文档：代码块必须 100% 原样 | 通用模型会"顺手改代码"，不可接受 |
| 阅读用，不追求可发布译文 | 可用模型规模受限 |

**核心矛盾**：8 GB 显存装不下"两个 7B/8B 模型"，也装不下大模型的完整上下文。
整个方案的参数都是围绕这一点推导出来的。

---

## 阶段 0 · 选型决策

| 决策 | 选择 | 放弃的方案与原因 |
|---|---|---|
| 推理引擎 | **llama.cpp 预编译版** | Ollama（模板/KV 量化不可控）、LM Studio（参数控制少）、源码编译（要装 VS + CUDA Toolkit，收益低） |
| 模型 | **Qwen3-8B Q4_K_M**（4.68 GiB） | 曾考虑 Hunyuan-MT-7B：纯翻译质量更高，但**官方 prompt 极简、装不下术语表和格式规则**，而 Qwen3 能听懂"不许动代码""按术语表翻"这类约束 |
| 是否需要自建网关 | **需要** | 插件直连模型有三个致命问题：代码块会被翻、标识符会被改、漏译无人检测 |
| 量化等级 | Q4_K_M | 8B 的"质量拐点"，权重 4.68 GiB 在 8 GB 卡上留出 KV 空间 |

**关键认知**：这不是"选一个最强的模型"，而是"在 8 GB 约束下选一个能被规则约束住的模型"。

## 阶段 2 · 安装推理引擎

**下载两个包**（缺一不可），版本必须是 **CUDA 12.4**（对齐驱动）：

| 文件 | 作用 |
|---|---|
| `llama-b10992-bin-win-cuda-12.4-x64.zip` | 主程序（含 `llama-server.exe`） |
| `cudart-llama-bin-win-cuda-12.4-x64.zip` | CUDA 运行时 + cuBLAS |

**两个坑**：

1. **不要走 `/releases/latest`** —— 它当时指向一个不含二进制包的 release（`v0.4.1`），白找一圈。
   要打开 `/releases` 列表页，找 **`b` 开头的构建号**。
2. `github.com` 直连不通（`curl` 返回 `000`）→ 下载链接前拼 `https://ghfast.top/`。

**解压**：两个 zip 都解压到 `D:\ai\llama`，同名文件选择"替换"。

**验证**：

```powershell
D:\ai\llama\llama-server.exe --list-devices
```

看到 `CUDA0: NVIDIA GeForce RTX 4060 Laptop GPU (8187 MiB, ...)` 才算成功。

```powershell
pip install -U "huggingface_hub"
```

**校验**（HF tree API 里字段叫 `lfs.oid`）：

```powershell
$t = curl.exe -sL "https://hf-mirror.com/api/models/Qwen/Qwen3-8B-GGUF/tree/main" | ConvertFrom-Json
($t | Where-Object { $_.path -eq 'Qwen3-8B-Q4_K_M.gguf' }).lfs.oid
```

**为什么必须先校验**：4.7 GB 下载被截断很常见，而 llama.cpp 对损坏的 GGUF 只会抛一句很难懂的错误。

## 阶段 4 · 推导服务参数（最关键的一步）

### 显存预算公式

```
可用显存 ≈ 总显存 − 桌面占用(约 1 GB)
开销 = 权重 + KV 缓存 + 计算缓冲(约 0.5 GB) + CUDA 上下文(约 0.3 GB)
```

**KV 缓存怎么算**（Qwen3-8B：36 层、8 个 KV 头、head_dim 128）：

| 精度 | 每 token 每层 | × 36 层 |
|---|---|---|
| fp16 | 2(K+V) × 8 × 128 × 2 B = 4096 B | **144 KiB / token** |
| q8_0 | 约 1 B/数值 ≈ 2176 B | **约 78 KiB / token** |

于是：

| 上下文 | KV（q8_0） |
|---|---|
| 8192 | 0.61 GB |
| **12288** | **0.92 GB** |
| 16384 | 1.22 GB |

### 定下来的参数

| 参数 | 值 | 理由 |
|---|---|---|
| `-ngl 99` | 全部层上 GPU | 4.68 GiB 权重全进显存 |
| `-c 12288` | 总上下文 12K | KV 约 0.92 GB，总占用 ≈ 6.4 GB，留 ~0.7 GB 余量 |
| `--parallel 2` | 2 个并发槽 | 每槽 6144 token；与插件并发对齐 |
| `-fa on` | Flash Attention | 省显存 + 提速；**KV 量化依赖它** |
| `--cache-type-k/v q8_0` | KV 量化 | 把 KV 从 1.9 GB 压到 0.92 GB，是能开 12K 的前提 |
| `--jinja` | 用 GGUF 内嵌模板 | Qwen3 对话模板必需 |
| `--temp 0.2 --top-p 0.8 --top-k 20` | 采样 | 技术文档求稳；网关请求会覆盖 |

**实测对照**：预测 ≈6.4 GB，`nvidia-smi` 实测 **6340 MiB** —— 公式可用。

> **换机器怎么定 `-c`**：先算 `权重 + 0.8 GB`，剩下的显存除以"每 token KV 大小"就是能开的上下文。
> Qwen3-8B Q4_K_M + q8_0 KV 的经验值：**每 1000 token 约 76 MiB**。

## 阶段 5 · 起服务并验证 GPU 生效

```powershell
D:\ai\llama\llama-server.exe -m D:\ai\mt\models\Qwen3-8B-Q4_K_M.gguf --alias qwen3-8b --host 127.0.0.1 --port 8080 -c 12288 --parallel 2 -ngl 99 -fa on --cache-type-k q8_0 --cache-type-v q8_0 --jinja --temp 0.2 --top-p 0.8 --top-k 20
```

日志关键行：

```
n_slots = 2, n_ctx_slot = 6144        ← 上下文切分正确
model loaded
listening on http://127.0.0.1:8080
```

**GPU 生效的两条铁证**（新版 llama.cpp 日志精简了，别去找 `offloading` 那行）：

```powershell
nvidia-smi --query-gpu=memory.used,memory.free --format=csv
# → 6340 MiB, 1618 MiB      权重确实在显存里
```

外加一次实测请求，看 `timings.predicted_per_second` ≈ 40–55 即正常。

## 阶段 6 · 为什么需要网关

插件直连模型会出三类问题，网关就是来解决它们的：

| 问题 | 演示 | 网关对策 |
|---|---|---|
| 代码被改 | `get_user_by_id` → `getUserById`；缩进/分号被"美化" | **代码块整块不进模型**，还原时用原文逐字节贴回 |
| 标识符被翻 | `--verbose` → `-- 详细` | 行内标识符掩码（flag / 常量 / 版本号 / 调用） |
| 漏译无检测 | 长段只翻一半 | 占位符校验 + 长度比 + 句数检测 → 重试 → 兜底回原文 |

**核心设计思想**：*不是让模型守规矩，而是设计一个"即使它不守规矩也不会出事"的流程。*
代码的字节从头到尾存在程序侧（"保险箱"），模型只看到 `[[ph0]]` 这样的引用，改也改不到。

**验收方法（最省事的一条）**：翻译完后在页面上 `Ctrl+F` 搜 `--verbose`。
**能搜到 = 标识符没被改**。

## 阶段 9 · 踩坑时间线（前人经验）

| # | 坑 | 症状 | 根因 | 修法 |
|---|---|---|---|---|
| 1 | `/releases/latest` 陷阱 | 找不到 Windows 包 | latest 指向无资产的 release | 走 releases 列表找 `b` 号 |
| 2 | GitHub 直连被墙 | 下载超时 | 网络 | 加 `https://ghfast.top/` 前缀 |
| 3 | PowerShell 挂死 | `Invoke-RestMethod` 卡住不动 | .NET 读 IE 代理 + 无 Happy Eyeballs | 改用 `curl.exe` |
| 4 | `.ps1` 中文乱码 | `字符串缺少终止符` | UTF-8 无 BOM 被按 GBK 解码 | 存 UTF-8 with BOM；或脚本改纯 ASCII |
| 5 | `>nul` 报错 | `FileStream 打开一个不是文件的设备` | PowerShell 不认 cmd 的 `nul` | 用 `> $null` |
| 6 | 多个 Python | `pip` 装了但 `import` 失败 | PATH 首位是 MSYS2 的 Python | 全部用绝对路径 |
| 7 | **502 Bad Gateway** | 网关一转就报错 | httpx 读到系统代理 `127.0.0.1:7993` | `httpx.AsyncClient(..., trust_env=False)` |
| 8 | **长段落变英文** | 短句正常、长段弹窗 | 句数检测要求中文句号后有空格 | 中文标点独立计数（P2 补丁） |
| 9 | GitHub commit 不翻 | 只有 commit 正文没译 | 插件默认跳过 `<pre>`/`<code>` | 划词翻译 / 站点规则 / 油猴脚本 |

## 附 · 换机迁移清单

| 步骤 | 动作 |
|---|---|
| 1 | 装 NVIDIA 驱动（对齐目标 CUDA 版本） |
| 2 | 装 Python（勾选 Add to PATH），`python -m pip install fastapi "uvicorn[standard]" httpx` |
| 3 | 建目录 `D:\ai\llama`、`D:\ai\mt\models`、`D:\ai\mt\logs`、`D:\ai\docs` |
| 4 | 从 releases 下 `llama-*-bin-win-cuda-12.4-x64.zip` + `cudart-*-bin-win-cuda-12.4-x64.zip`，解压合并且规整到根目录 |
| 5 | 用 hf-mirror 下模型，**校验 sha256** |
| 6 | 拷 `local-mt-gateway.py`（**确认 P1/P2 两个补丁都在**） |
| 7 | 按新机器显存重算 `-c`（每 1000 token 约 76 MiB 经验值） |
| 8 | 建两个 bat（用绝对路径） |
| 9 | 起服务 → `--list-devices` + `nvidia-smi` + curl 三连验证 |
| 10 | 配插件 → `Ctrl+F` 验收 |

**一句话总结这套方案**：
*在 8 GB 显存约束下，用"通用模型 + 确定性工程约束"替代"更大模型"，把钱和算力花在"可信度"而不是"参数量"上。*
